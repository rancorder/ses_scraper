# SES Drive URL Agent

This layer runs the existing SES screening pipeline without changing scoring logic or profiles.

## CLI

### Drive URL mode

```bash
python agent/run_job.py \
  --drive-url "https://docs.google.com/spreadsheets/d/FILE_ID/edit" \
  --profile t2_lab \
  --output-folder-url "https://drive.google.com/drive/folders/FOLDER_ID"
```

### Local VPS validation mode

```bash
python agent/run_job.py \
  --local-file "./webui/uploads/t2_test_10rows.csv" \
  --profile t2_lab \
  --no-upload
```

Optional controls:

```bash
--retries 2   # retry failed Drive/download, evaluation/merge, and upload actions
--force       # remove an existing agent lock; only after confirming no job is running
```

## Job status CLI

```bash
python agent/job_status.py --latest
python agent/job_status.py --job-id JOB-20260905-075344-806093
python agent/job_status.py --failed
python agent/job_status.py --failed --limit 3
```

`--job-id` reads the live per-job `job.json` first, so it can also show the current state of a job that has not yet reached terminal history. `--latest` and `--failed` read the append-only `work/jobs.jsonl` terminal history.

## Requirements

- Existing project virtualenv and Python dependencies
- `rclone` installed on the VPS
- Existing Google Drive remote (default: `gdrive`, configurable in `config/agent.yaml`)
- The authenticated Drive account must be able to read the input resource and write to the output folder

## Flow

Drive URL -> rclone download/export -> existing `batch_run.py` -> collect job-specific batch outputs -> existing `merge_results.py` -> rclone upload -> Drive file URL

The Agent gives each input a unique job-id prefix. This allows it to collect only the batch files generated by that job from the legacy `company_analyzer/output` directory and move them into `work/{job_id}/output` before merging.

The runner calculates the expected number of batches before execution. If `batch_run.py` exits successfully but one or more batches were not generated, the job fails instead of uploading a partial merged result.

## Job management

- Global lock: `work/.agent.lock`
- Per-job state: `work/{job_id}/job.json`
- Per-job execution log: `work/{job_id}/logs/execution.log`
- Per-job output: `work/{job_id}/output/`
- Append-only history: `work/jobs.jsonl`
- Job IDs include microseconds to avoid collisions under rapid launches
- Default retry policy: 1 retry with 5 seconds delay (`config/agent.yaml`)

If a lock remains after an abnormal shutdown, first verify that no Agent job is running. Only then use `--force` to remove the stale lock.

## Retry semantics

Retries are intentionally applied only to operations that can plausibly recover on a second attempt:

- Drive download/export
- evaluation + merge execution
- Drive upload

Preflight/validation failures are not retried. Examples include:

- local input file does not exist
- invalid profile
- invalid URL / unsupported input format
- lock already exists

For these failures, `attempts` may remain `0` because the retryable execution stage was never entered. This is expected behavior and avoids waiting on deterministic configuration errors.

## Phase 2 verification

```bash
python -m py_compile agent/*.py
python agent/run_job.py --help
python agent/run_job.py \
  --local-file "./webui/uploads/t2_test_10rows.csv" \
  --profile t2_lab \
  --no-upload

tail -5 work/jobs.jsonl
ls -la work/.agent.lock
python agent/job_status.py --latest
python agent/job_status.py --failed --limit 3
```

Verified on VPS (2026-09-05):

- normal 10-company `t2_lab` run -> `COMPLETED`, `attempts: 1`
- terminal record appended to `work/jobs.jsonl`
- lock removed after normal completion
- existing lock -> immediate `FAILED`, `attempts: 0`
- nonexistent local file -> immediate `FAILED`, `attempts: 0` (non-retryable preflight failure)
- retryable evaluation failure with `--retries 2` -> 3 attempts then terminal `FAILED`

After a normal completed run, `work/.agent.lock` should not exist. The terminal job record should be appended to `work/jobs.jsonl`.
